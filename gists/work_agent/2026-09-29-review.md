# MountWizzard4 – Code & Architecture Review

**Date:** 2026-09-29
**Previous review:** [2026-06-10-review.md](2026-06-10-review.md)
**Scope:** `src/mw4` (logic, gui, base, mountcontrol) and `tests/unit_tests`
**Baseline:** `671cdfce6` (beta34, 567 commits since the previous review)
**Dimensions reviewed:** PySide6 / Qt6 usage, Pythonic style, architecture,
simplicity, performance, maintainability, test health.

> This is an assessment with prioritized recommendations. It does **not** change
> any code. Findings point to concrete files and symbols so they can be acted on

## 1. Executive Summary

Since the June review the codebase has improved noticeably. Six of the ten
recommendations are **fully resolved**: the pragmas, misplaced docstrings,
magic mount status codes, repetitive `addDevices`, per-second twilight and disk
computation, hard-coded thread count, and the missing `TabAddon` contract. Ruff
reports no findings and the full suite (4545 tests) passes serially.

The open items are the same structural ones as before: the **nested event loop
sleep** (`mainThreadSleep`), which now also runs inside the model build **logic**
layer, the **`app: Any` seams**, and the **untyped app-level signal hub**. The
new findings are about **dead leftovers from the reverted Alpaca server
discovery**, **test isolation under `pytest-xdist`**, and a **coverage setup
that does not yet match the Windows-only coverage policy**.

**Overall maturity rating:** Strong (4 / 5), trending up.

## 3. PySide6 / Qt6

### 3.1 `mainThreadSleep` now also drives model build logic (High)

[`base/threadUtils.py`](../../src/mw4/base/threadUtils.py) still runs a nested
`QEventLoop` to "sleep". Current call sites:

| File                                        | Line(s)   | Use                                            |
|---------------------------------------------|-----------|------------------------------------------------|
| `logic/modelBuild/modelRun.py`              | 211, 307  | Wait/pause loop and **main batch loop**        |
| `gui/mainWaddon/tabModel.py`                | 196       | 1 s pause                                      |
| `gui/mainWindow/externalWindows.py`         | 180       | 50 ms between window closes                    |
| `gui/extWindows/video/videoBase.py`         | 142       | 1 s pause                                      |
| `gui/extWindows/downloadPopupW.py`          | 156       | 500 ms pause                                   |
| `gui/extWindows/uploadPopupW.py`            | 202, 209  | Polling + pause                                |
| `gui/extWindows/analyseW.py`                | 464       | `mainThreadSleep(0)` used as `processEvents()` |

The worst case is `ModelRun.runThroughModelBuildData`:

```python
while not self.cancelBatch and not self.endBatch and not self.checkModelFinished():
    mainThreadSleep(500)
```

For the whole model run, the application runs inside a nested event loop. Any
re-entrant signal (start another model, close the window, switch profile) runs
on top of that stack. The code is also in the **logic** layer but depends on a
Qt event loop helper, which weakens the logic/GUI separation.

**Recommendation:** Make the model run event-driven. Replace the batch loop with
a state machine that moves forward on the existing signals (slew finished, image
saved, solve result), and use `QTimer.singleShot` for the timed waits. The GUI
helpers in `externalWindows`, `videoBase`, and the popups can use
`QTimer.singleShot(ms, continuation)` directly.

### 3.2 `QApplication.processEvents()` inside population loops (Medium)

[`tabAsteroid.py`](../../src/mw4/gui/mainWaddon/tabAsteroid.py) (l. 172),
[`tabComet.py`](../../src/mw4/gui/mainWaddon/tabComet.py) (l. 173) and
[`tabTools_Rename.py`](../../src/mw4/gui/mainWaddon/tabTools_Rename.py) (l. 142)
call `processEvents()` once per table row. This has the same re-entrancy risk as
3.1, and it slows large lists because every row triggers a full event pass.

**Recommendation:** Fill the table with `setUpdatesEnabled(False)` / `True`
around the loop, or insert the rows in chunks with `QTimer.singleShot(0, …)`.
For large catalogs, a `QAbstractTableModel` with a `QTableView` removes the
per-item cost completely.

### 3.3 Untyped signal payloads (Low/Medium, unchanged)

There are still 53 `Signal(object, …)` declarations. The main ones are
`mountcontrol/mountSignals.py` (12), `mainApp.py` (10) and
`gui/extWindows/keypadW.py` (8). `MountWizzard4.msg = Signal(object, object,
object, object)` is emitted with `(int, str, str, str)` everywhere and should be
typed like that.

### 3.4 Teardown noise in the test run (Low)

A serial full run ends with `QMutex: destroying locked mutex` and `RuntimeError:
Signal source has been deleted` from `MountTime.runnerMountUp`. That means a
worker still emits after its owning `QObject` has been deleted. It is harmless
in tests, but at application shutdown the same pattern can crash. Wait for the
worker or disconnect it before the owner goes away (the same approach as
`threadPool.waitForDone` in `closeEvent`).

## 4. Architecture

### 4.1 `app: Any` seams (Medium, unchanged)

53 constructors take `app: Any` and 24 take `mainW: Any`. This is still the
biggest gap between the strong typing policy and the real dependency surface.
The proposal in
[`2026-06-10-proposal-rec4-AppProtocol.md`](2026-06-10-proposal-rec4-AppProtocol.md)
is still valid. Now that `TabAddon`, `DeviceRegistry`, and `TimeManager` are
stable, it is a good time to implement it.

### 4.2 Dead code left from the reverted Alpaca server discovery (Medium, new)

Commit `9640a77f1` moved server discovery to a feature branch, but
[`devicePopupW.py`](../../src/mw4/gui/extWindows/devicePopupW.py) still contains:

- `setAlpacaServer()` (l. 278–283), which reads `self.ui.alpacaServerList`. That
  widget no longer exists in the generated UI or in `src_add/widgets`.
- The `elif framework == "alpacaServer":` branch in `discoverDevices` (l. 299–300),
  which calls `deviceInstance.discoverDeviceServer()`. That method is not
  defined anywhere in `src/mw4`.

Both paths are unreachable today and would raise `AttributeError` if they were
reached. They are also the only uncovered non-Windows lines in that module.

**Recommendation:** Remove both on the main branch and keep them only on the
feature branch.

### 4.3 Test hooks in production code (Low, unchanged)

`MountWizzard4(test: int = 0)` (connects `update10s` to `mainW.close`) and the
`hasattr(app, "mount")` injection in `DeviceRegistry.__init__` are still there.
Passing the mount instance (or a factory) into `DeviceRegistry` would keep the
production path free of test concerns.

## 5. Correctness Observations

### 5.1 Unit of `waitTimeExposure` (Low, needs checking)

In `ModelRun.startNewImageExposure`:

```python
waitTime = self.waitTimeExposure
while self.pauseBatch or waitTime > 0:
    mainThreadSleep(500)
    waitTime -= 1
```

The spin box (`waitTimeExposure`, 0–300, 0 decimals) reads as seconds. The loop
takes off one unit every 500 ms, so the real wait is **half** the configured
value. Check which unit is intended and either sleep 1000 ms per step or
subtract 0.5. This goes away with the timer-based rewrite from 3.1.

### 5.2 Broad `except Exception` in `tabSat_Search` (Low)

`SatSearch` (l. 280) catches `Exception` around the whole filter loop and logs
at `debug`. Real failures are hidden, and `sat` may be unbound in the log
message if the exception happens before the first iteration. Catch only the
expected exceptions and log at `warning`.

### 5.3 Dead branch in `AlpacaAscomCommon.getDeviceProp` (Low)

```python
if valueProp == "ImageArray":
    pass
```

This branch does nothing (l. 54–55). It is the only uncovered line in the
module. Remove it.

### 5.4 `PlateSolve.runSolverBin` (Informational)

The recent refactor to `communicate(timeout=…)` with `kill()` + drain on
timeout is correct and fully covered. Small cleanup: in the timeout branch,
`stdout, _ = self.process.communicate()` assigns a value that is never used, so
`self.process.communicate()` alone is enough.

## 6. Performance

- The single 100 ms timer with fan-out and the move of twilight/disk to 30 s are
  good.
- `ModelRun` busy-waits every 500 ms for the whole run (3.1). An event-driven
  flow removes that wake-up and the nested loop.
- `processEvents()` per table row (3.2) is the main UI performance problem for
  large asteroid/comet catalogs.
- Blocking `time.sleep` only runs in worker threads (`cameraSGPro`,
  `sgproClass`, `kmRelay.runnerPulse`), which is fine.

## 7. Test Health

| Metric                               | Result                                          |
|--------------------------------------|-------------------------------------------------|
| Ruff check / format                  | ✅ clean (463 files)                            |
| Serial run (`pytest tests/unit_tests`) | ✅ 4545 passed, 38 skipped, ~19 s             |
| Parallel run (`-n auto`)             | ❌ 10 failed, 44 skipped (all pass serially)    |
| Coverage (macOS, serial)             | 99 % (63 of 18,461 statements missed)           |

### 7.1 Tests are not isolated under `pytest-xdist` (Medium, new)

`pytest-xdist` is installed, but with `-n auto` these tests fail. All of them
pass serially:
`test_tabMount_Sett::test_updateSettingGUI_10..14`,
`test_measure::test_checkStart_1/2`, `test_modelRun::test_checkModelFinished_2`,
`test_modelRunSupport::test_loadModelsFromFile_2`,
`test_profile::test_loadProfileStart_3`.
The likely causes are the shared `tests/work/*` directories that module-scoped
fixtures write to and delete (e.g. `glob.glob("tests/work/image/*.fit*")` +
`os.remove`), and test-order-dependent module fixture state.

**Recommendation:** Use `tmp_path` / `tmp_path_factory` for file artifacts, or
mark the affected modules with `xdist_group`. Also set values that a test
depends on inside that test rather than relying on earlier tests.

### 7.2 Coverage config does not match the Windows policy (Low/Medium, new)

The project policy is to write Windows tests but count them for coverage only on
Windows. On macOS almost all of the missing 1 % is Windows-only code:
`base/ascomClass.py` (37 %), `logic/camera/cameraAscom.py` (0 %), and the
`if platform.system() == "Windows":` imports/branches in `camera`, `cover`,
`dome`, `filter`, `focuser`, `lightPanel`, `sensorWeather`, `telescope`, and
`pegasusUPB`. `[tool.coverage]` has no platform-dependent exclusion, so a
100 % gate can never pass on macOS or Linux.

**Recommendation:** Add platform-conditional coverage (for example
`coverage-conditional-plugin` with a `sys_platform != "win32"` rule, or a
per-OS `omit` for the `*Ascom*.py` modules). After that, the only real
non-Windows gaps are `alpacaAscomCommon.py:55` (5.3),
`indiClass.py:144` (`discoverMutex.tryLock()` contention path, needs a test),
and `devicePopupW.py:279-283, 300` (4.2, to be deleted).

### Suggested sequencing

1. **Quick wins (S):** 3, 5, 7, 8, 11. These are low risk and bring
   non-Windows coverage to a real 100 %.
2. **Test infrastructure (M):** 4. This makes `-n auto` usable and shortens
   feedback loops.
3. **Typing (M):** 6, then 9 on top of the `Protocol`.
4. **Concurrency refactor (L/M):** 1, then 2. This needs a short plan first
   because it touches `ModelRun`, `tabModel`, and the model status GUI.

## 9. Closing Note

Most of the June review has been implemented, and the code is cleaner, more
data-driven, and easier to type. The remaining structural risk is in one place:
the nested event loop used to sequence long operations, which now sits at the
core of the model build. Fixing that (#1) is the most valuable change. The
cheapest wins are removing the dead Alpaca-server code (#3) and making coverage
platform-aware (#5), which together let the project enforce its 100 % coverage
rule on every OS.
